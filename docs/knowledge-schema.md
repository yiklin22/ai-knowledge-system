# Knowledge Schema — version 2

The contract for everything in `vault/`. `tools/kb` enforces the mechanical parts (`./kb validate`).

## 1. What the knowledge base contains

Reading is turned into **eight kinds of entity**. Each answers a different question, so they stay separate:

| type | folder | id prefix | Answers | Typical origin |
|---|---|---|---|---|
| `source` | `sources/` | `src` | *What did I read, how reliable is it, where exactly is the evidence?* One per ingested item, with a locator map and a reliability grade. | every item in `raw/` |
| `concept` | `concepts/` | `cpt` | *What is this idea / technique / term?* Domain-tagged, with aliases and optional recall cards. | articles, papers, videos |
| `claim` | `claims/` | `clm` | *What is asserted, and does the evidence hold up?* One atomic, testable statement, with supporting and contradicting evidence. This is where disagreement between sources lives. | any source |
| `entity` | `entities/` | `ent` | *Who/what is it?* People, organizations, papers, books, models, products, benchmarks, tools, datasets. | any source |
| `question` | `questions/` | `qst` | *What do I not yet know?* A curiosity queue; claims and insights can answer a question. | gaps found while reading |
| `insight` | `insights/` | `ins` | *What did **I** conclude, decide or learn?* Lessons, decisions, preferences, principles. Always the author's view, never presented as source fact. | my chats with AIs, my work |
| `project` | `projects/` | `prj` | *What am I building or deciding?* Work and life projects that knowledge gets applied to. | work documents |
| `map` | `maps/` | `map` | *Where do I start in this area?* Hand-curated hub per domain or learning path (Obsidian "map of content"). | the human |

**Domains** (`vault/domains.yml`) are a controlled vocabulary that makes the system multidisciplinary: AI, programming, work, science, etc. Every page lists one or more. New domains are added to the file deliberately, never invented ad hoc.

**Learning layer.** A concept may carry `recall` cards (`q`/`a`). Cards are synced into SQLite (`data/learning.db`) where spaced-repetition progress lives. Progress never touches the vault.

## 2. Identity

- `id` = `<prefix>_<8 chars [a-z0-9]>`, e.g. `cpt_k3x9a2mq`. Generated by `./kb new`; never typed by hand, never reused, **never changed**.
- Filenames are human slugs (`retrieval-augmented-generation.md`) and may be renamed; nothing identifies a page by filename except `[[wikilinks]]` in prose, which are checked on every validate (rename a page → fix links).
- Frontmatter relations, citations and learning cards reference **ids only**.
- Every page has `schema: 2`. A schema change bumps the number and ships with a migration note in `vault/log.md`.

## 3. Frontmatter

Common to all types (all required; use `[]`/`null` rather than omitting):

```yaml
id: cpt_k3x9a2mq
schema: 2
type: concept
title: Retrieval-Augmented Generation
aliases: [RAG]
domains: [ai]
summary: One or two plain sentences. Shown in the index.
tags: [retrieval]
status: draft            # stub | draft | reviewed | outdated | deprecated
confidence: medium       # low | medium | high
created: 2026-11-08
updated: 2026-11-08
sources:                 # citations; each id must be a `source` page
  - id: src_ab12cd34
    locator: "12:30"     # page, section or timestamp. Required if quote is set
    quote: null          # exact text from the raw file, or null
relations:
  - {rel: broader, id: cpt_zz99yy88}
  - {rel: related, unresolved: "Vector databases"}   # target not in the vault yet
```

`status: reviewed` means a human approved the content. `confidence: high` requires two or more independent sources or one primary source.
`sources` may be `[]` only for `stub` pages and for `insight`, `question`, `project`, `map` (author-originated).

Type-specific required fields:

| type | field | allowed values |
|---|---|---|
| source | `kind` | chat, document, web, video, paper, book, note |
| source | `reliability` | primary, secondary, vendor, ai-chat, opinion |
| source | `raw` or `url` | path in `raw/` (must exist) and/or URL; at least one |
| entity | `kind` | person, organization, paper, book, model, product, benchmark, tool, dataset |
| claim | `verdict` | unverified, supported, contested, refuted |
| question | `state` | open, answered, parked |
| insight | `kind` | lesson, decision, preference, principle |
| project | `state` | idea, active, paused, done |
| concept | `recall` (optional) | list of `{q, a}` flashcards |
| concept | `probes` (optional) | Socratic prompts: list of `{q, looks_for}`; `looks_for` is the understanding a good answer shows |
| concept | `misconceptions` (optional) | list of common wrong beliefs, each a short sentence, for the tutor to test for |
| any | `volatile` (optional) | `true` for pricing, rankings, capabilities; needs `last_verified` |

## 4. Relationships

Typed, written on **one side only**; inverses are derived by `./kb build` (no manual two-way bookkeeping).

| rel | inverse | typical use |
|---|---|---|
| `related` | `related` | loose association |
| `broader` | `narrower` | concept hierarchy |
| `part_of` | `has_part` | composition |
| `prerequisite_for` | `requires` | **learning order**: read A before B |
| `supports` | `supported_by` | claim/evidence → claim |
| `contradicts` | `contradicts` | documented conflict |
| `qualifies` | `qualified_by` | "true, but only if…" |
| `derived_from` | `gave_rise_to` | insight/claim → source or insight |
| `answers` | `answered_by` | claim/insight → question |
| `about` | `discussed_in` | any → concept/entity |
| `introduced_in` | `introduces` | concept/entity → source/entity |
| `authored_by` | `authored` | source/entity → entity |
| `affiliated_with` | `has_affiliate` | entity → entity |
| `supersedes` | `superseded_by` | replacement |
| `applies_to` | `applied_by` | concept/insight → project |
| `contains` | `contained_in` | map → anything |

A relation target is either `id: <existing id>` or `unresolved: "<name>"`. Unresolved entries are legal (validate reports them as warnings) so nothing is lost when the target page doesn't exist yet. Proposing the missing page resolves it.

## 5. Epistemic rules

- Tag every claim sentence in Evidence/Understanding/Uncertainty sections: `[fact]` (stated by a cited source), `[inference]` (synthesis, says what it rests on), `[speculation]` (only in Uncertainty).
- An AI chat is not evidence. Facts learned only from an AI chat are `[inference]`, source `reliability: ai-chat`, `confidence: low`, until a primary source backs them.
- Vendor claims are written as vendor claims (`reliability: vendor`).
- Never fabricate citations, quotes or locators. `validate` checks that each `quote` appears verbatim (whitespace-normalised) in the cited source's raw file; a quote on a URL-only source cannot be verified and is rejected.
- Volatile facts carry the date inline and `last_verified`; older than 90 days → flagged stale.
- Contradiction: keep both views, create/extend a `claim` page with `contradicts` links. Do not overwrite.
- Human-authored text is wrapped in `<!-- human -->…<!-- /human -->`. `./kb approve --amend` refuses a change that alters or removes such a block.

## 6. Concept body

Non-stub concepts use these sections, in order (validate warns if missing): `Knowledge` (established facts), `Evidence` (how we know, with sources), `Understanding` (why it works; a Mermaid diagram for hard mechanisms), `Application` (when to use / not), `Uncertainty` (open or contested), `Related`.
Other types use short free-form bodies defined by their template (`./kb new`).

## 7. Lifecycle

`raw/` (immutable) → `proposals/<batch>/` (AI-written, unapproved) → human review → `./kb approve <batch>` → `vault/` (approved, canonical) → `./kb build` (derived: `build/kb.sqlite` full-text search + links, `build/graph.json`, `vault/index.md`). Derived files are disposable and can be rebuilt at any time.
